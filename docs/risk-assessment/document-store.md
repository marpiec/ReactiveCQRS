## Findings

### DOCS-1 — `findDocument`/`findAll`/`findDocumentByPath*` load an entire read model into heap (no default limit)
- **Severity:** High · **Likelihood:** Possible · **Confidence:** Confirmed (code)
- **Location:** `PostgresDocumentStore.scala:261-270` (`findDocument`→`createQuery`), `:418-426` (`findAll`), `:437-468` (`getDocuments`); `DocumentStore.scala:102` (`DocumentStoreQuery.basic` = `(where, Seq.empty, 0, -1)`), `:183-192` (`findDocumentByPath`, `findDocumentByPaths`), `:213-219` (`findDocumentsByPathWithOneOfTheValues`). All the convenience finders route through `DocumentStoreQuery.basic`, and `createQuery` emits a `LIMIT` only when `limit >= 0`:
  `(if(searchParams.limit >= 0) (" LIMIT " + searchParams.limit) else "")`.
- **Preconditions:** a read model (`projection_<name>`) that has grown large — in a multi-tenant SaaS, a per-type or cross-space model with millions of rows.
- **Triggering scenario:** a query handler calls `store.findDocumentByPath(Seq("status"), "active")`, or `findAll()`, or any `DocumentStoreQuery` built with the default `limit = -1`, and the predicate matches (or the table holds) millions of rows. `findDocumentByPath` is the single most natural call and is unbounded.
- **Failure mechanism:** `createQuery` builds `SELECT id, version, document FROM projection_x` with no `LIMIT`; `findDocument` does `.list()` — the whole result set is pulled, each `document` JSONB is `mpjsons.deserialize`d, and (with a cache) every row is also handed to `cacheAfterCommit`. The projection actor runs single-threaded, so while this builds a mult-GB `Seq`/`Map` it applies no updates and answers no other query; a large enough result OOMs the JVM. SCALING §1 documents owner/bus/outbox limits but has no row-count bound for document reads; the book says "for small read models only" for `findAll` only — the other unbounded finders carry no such guard and are the common case.
- **Impact:** a long GC pause or OutOfMemoryError that takes the node down (and, in a cluster, triggers rebalance/failover). Hard to detect until it fires in production; a query that was cheap when the model was small becomes fatal as a tenant grows.
- **Validation:** insert ~2M rows into a `projection_x`, call `findDocumentByPath(path, commonValue)` from a query handler with a bounded heap; observe the heap climb and the actor stall. Compare with the same query at `limit = 1000`.
- **Recommended fix:** give `DocumentStoreQuery.basic` and the `findDocumentByPath*` convenience methods a configurable default cap (e.g. a store-level `maxUnboundedRows`) and either throw or log-and-truncate past it; keep an explicit `findAllUnbounded`/`limit = -1` escape hatch for small models. Trade-off: a cap can silently drop rows, so it must be loud (log + metric) and documented, and callers that truly need all rows must opt in.
- **Regression test:** a store with N+1 rows, a `findDocumentByPath` capped at N, asserts an error or a truncation signal rather than N+1 rows; `findAll()` keeps returning all for a small model.

### DOCS-2 — JSON paths and sort fields are interpolated into SQL unescaped (`SQL(s"...")`); breaks on, or can be injected through, special characters
- **Severity:** High · **Likelihood:** Unlikely · **Confidence:** Confirmed (code)
- **Location:** `PostgresDocumentStore.scala:221-238` (`createQuery` sort), `:240-259` (`createPartsQuery` parts + sort), `:338-358` (`whereClause`/`constructWhereClauseForExpectedValues`), `:124-153` (`indexSql`/`pathsToQuery`). Every one builds fragments like `"document #>> '{" + path.mkString(",") + "}'"` and the sort `"(document#>'{"+path.mkString(",")+"}')::int ASC"` straight into `SQL(s"...")`. Only the *values* are bound (`getAllValues`, F158/F159); the *paths* and *sort fields* are not bound and not validated.
- **Preconditions:** a path element or sort-field name that contains `}`, `'`, `,`, or `\`. Two sub-cases: (a) a legitimate JSON field whose name contains a comma/brace/quote; (b) a host that builds a `DocumentStoreQuery` path or `Sort` from end-user input (e.g. "sort by the column the UI picked", "filter on this attribute name").
- **Triggering scenario:** (a) a document with a field literally named `"a,b"` → path `Seq("a,b")` becomes `{a,b}`, which PostgreSQL reads as the two-element path `a→b`, so the query silently targets the wrong field (wrong results). (b) a path element `x}' = '' OR '1'='1` or `x}'::int)::text) ; ...` closes the `#>>'{...}'` fragment and appends arbitrary SQL — classic injection, with end-user data per the stated threat model.
- **Failure mechanism:** `constructWhereClauseForExpectedValues` returns `document #>> '{<path>}' = ?`; the `?` is safely bound, but `<path>` is `mkString(",")` of raw strings. There is no analogue of the `tableName.matches("[a-zA-Z0-9_]+")` guard (line 26) or `ProjectionBuild.checked` for query/sort/index paths.
- **Impact:** at best wrong rows for exotic field names (a correctness bug, silent); at worst SQL injection if a path/sort ever carries user input — reading or modifying any tenant's data (GDPR-relevant).
- **Validation:** `findDocumentByPaths(ExpectedSingleTextValue(Seq("name}' OR version>'0"), "x"))` and assert the generated SQL is malformed/parameterised rather than executed; a field named `"a,b"` returns the field, not `a→b`.
- **Recommended fix:** validate every path element and sort field against a strict allowlist (letters, digits, underscore — matching the table-name rule), or build the `text[]`/path with proper escaping and pass it as a bound `?::text[]` the way `findDocumentByObjectInArray` now does for its array path (`:393`). Trade-off: an allowlist forbids JSON keys with punctuation; if those exist in Neula's documents, escape-and-bind instead.
- **Regression test:** a path element with `'`, `,`, `}` either errors clearly or is bound; a document key with a comma is matched correctly.

### DOCS-3 — `MemoryDocumentStore.findDocument` ignores `sortBy`, `offset` and `limit`
- **Severity:** Medium · **Likelihood:** Likely · **Confidence:** Confirmed (code)
- **Location:** `MemoryDocumentStore.scala:28-47` — `findDocument` is `store.filter(where-predicates).seq.toSeq`; it never looks at `query.sortBy`, `query.offset` or `query.limit`. `findDocumentByObjectInArray` (`:99-101`) likewise ignores its `limit`.
- **Preconditions:** a level-2 (in-memory) test, which the book and testkit actively encourage (`docs/book/19-testing.md` §"Level 2"), exercising a paged or ordered query.
- **Triggering scenario:** a test of `FindBigCarts` (`DocumentStoreQuery(..., sortBy = Seq(SortDescInt(...)), limit = 20)`) against `MemoryDocumentStore` returns *all* matching documents in `ParHashMap` iteration order. The test asserts on the set of results and passes; in production (`PostgresDocumentStore`) the same call returns only the top 20 in sorted order.
- **Failure mechanism:** the memory double is meant to "mirror `PostgresDocumentStore.createQuery` so tests see the same results" (comment at `:27`), but it only mirrors the `where` conditions, not ORDER BY/LIMIT/OFFSET. F14/F156/F159 fixed the conditions and spaces but left paging/ordering unimplemented, and it is not recorded as a documented gap (unlike instant reads / permanent delete at F14).
- **Impact:** paging and ordering bugs (wrong page, wrong order, off-by-one offsets, a query that should cap at N returning everything) pass level-2 tests and reach production undetected. For a tenant-facing list this is wrong results and, with DOCS-1, an unbounded fetch that tests never flagged.
- **Validation:** insert 50 documents, `findDocument(DocumentStoreQuery(Nil, Seq(SortDescInt(Seq("n"))), 0, 10))` against the memory store — it returns 50 unordered; against Postgres, 10 sorted.
- **Recommended fix:** apply `sortBy`, then `offset`/`limit` in `MemoryDocumentStore.findDocument` (and honour `limit` in `findDocumentByObjectInArray`); or, if that is deferred, add it to the documented test-double gaps so authors test ordered/paged queries at level 3. Trade-off: implementing sort over reflected values needs comparable extraction, more code in a test double.
- **Regression test:** `MemoryDocumentStoreSpec` with sorted + limited queries asserted against the same expectation as `PostgresDocumentStoreSpec`.

### DOCS-4 — `SchemaLock`: a blocked DDL holder stalls every other node's startup for 5 minutes, then fails them
- **Severity:** Medium · **Likelihood:** Possible · **Confidence:** Strongly suspected
- **Location:** `SchemaLock.scala:25-46`. One advisory lock (`Key = 0x52435152L`) guards *all* schema initialization library-wide; `acquire` polls `pg_try_advisory_lock` every 50 ms up to `MaxWait = 5.minutes`, then `throw new IllegalStateException(...)`. Every `initSchema`/document-store `init` is wrapped in it (`PostgresEventStoreSchemaInitializer:12`, `SubscriptionsState:183`, `PostgresDocumentStore:42`, `TypesNamesState:50`, `ProjectionRegistry:89`, `CommandResponseState:66`, `PostgresSagaSchemaInitializer:11`, `Projections.retire:67`).
- **Preconditions:** two or more nodes starting together (cluster, D42/D71) or a start concurrent with heavy DB activity; a DDL statement inside the lock that blocks on a table lock it cannot get.
- **Triggering scenario:** node A holds the advisory lock and runs `ALTER TABLE events ADD COLUMN ...` / `CREATE INDEX` (`init` and `initSchema` issue plain, non-`CONCURRENTLY` DDL) while a long autovacuum or a long analytic query holds a conflicting lock on `events`/`aggregates`. A's DDL waits behind that lock; meanwhile A keeps the advisory lock. Nodes B, C poll for up to 5 minutes and then throw from `initSchema`, failing their readiness/startup.
- **Failure mechanism:** the advisory lock is session-level on a dedicated borrowed connection and is correctly released on crash (TCP close) and in `finally` — so this is not a permanent deadlock. But a *slow or blocked* (not crashed) holder converts "serialized init" into "every other node fails to start" after `MaxWait`. There is no `lock_timeout`/`statement_timeout` on the DDL (the comment at `:39` deliberately avoids session settings on the pooled connection), so a blocked DDL can sit far longer than any single node's patience.
- **Impact:** during an upgrade or a busy-window restart, nodes fail to come up with an opaque "schema lock was not free for 5 minutes" error even though nothing is wrong except contention; an operator sees a cluster that will not form.
- **Validation:** in one session hold `LOCK TABLE events IN SHARE MODE` (or run a long transaction touching it), start a node so its `createEventsAggregateVersionIndexWhenSmall`/`ALTER` blocks, then start a second node; observe the second time out after 5 minutes.
- **Recommended fix:** set a bounded `lock_timeout` on the DDL connection (reset/`RESET ALL` before returning it to the pool, or use a fresh non-pooled connection) so a blocked DDL fails fast and releases the advisory lock; log which node holds the lock and for how long; consider separate advisory keys per component so an event-store DDL stall does not block an unrelated document-store init. Trade-off: a `lock_timeout` makes init fail faster but needs a retry/backoff around the component.
- **Regression test:** hold a conflicting table lock, assert the initializer fails with a bounded lock-timeout error (not after 5 minutes) and releases the advisory lock so a second initializer proceeds once the conflict clears.

### DOCS-5 — `AfterCommit` keeps process-global static maps behind one JVM-wide monitor
- **Severity:** Medium · **Likelihood:** Possible · **Confidence:** Confirmed (code)
- **Location:** `AfterCommit.scala:19-21` (two static `java.util.IdentityHashMap`s), and every access synchronizes on the single `queued` monitor: `localTx` (`:29,39`), `local` (`:49`), `apply` (`:59`), `runQueued` (`:73`). This object backs *all* projection transactions (`SubscriptionsState.localTx:434`, `PostgresEventStoreState.localTx:859`) and every document-store cache write (`cacheAfterCommit:493-504`).
- **Preconditions:** many projections/stores committing concurrently — the default blocking dispatcher is 32 threads, and `parallelUpdateProcessing` adds more; or more than one `ActorSystem` in a JVM (tests, or a host embedding two).
- **Triggering scenario:** (1) contention — under high projection throughput every commit and every cached read across all projections serializes on one monitor to register/run after-commit actions; the critical sections are short (map put/get and running cache updates) but global. (2) shared global state — the maps are keyed by `DBSession` identity and are static, so they are shared by *all* actor systems in the JVM. Two systems that happen to run a transaction on the same pooled `java.sql.Connection` are distinguished only by the `DBSession` wrapper identity (the comment at `:18` relies on this); a pooling layer that reuses the same `DBSession` object, or a future change that does, would mix one system's deferred cache writes into another's transaction.
- **Failure mechanism:** correctness depends on `DB.localTx` minting a fresh `DBSession` per transaction (true today in ScalikeJDBC), and on `runQueued` being reached — `localTx` runs the queued actions *after* `DB.localTx` returns and removes them in `finally`; a non-`AfterCommit` `DB.localTx` (e.g. `ProjectionRegistry`, `SpacePurge`, `SpaceImport` all use bare `DB.localTx`) never registers, so cache writes inside those run immediately via the `apply` "not deferred" branch — which is correct, but means the deferral guarantee holds only for transactions opened through `AfterCommit.localTx`.
- **Impact:** a hidden global serialization point on the projection hot path (throughput ceiling under many parallel projections), and process-global mutable state that couples otherwise-independent actor systems. Hard to detect: shows up as lock contention in a profile, or as cross-system cache anomalies only under unusual pooling.
- **Validation:** profile a run with many projections on the 32-thread dispatcher and look for contention on `AfterCommit$`; or construct a test with two `ActorSystem`s sharing a pool and assert their deferred actions do not interleave.
- **Recommended fix:** carry the deferred-action list on the session itself (ScalikeJDBC supports attributes) or in a `ThreadLocal` scoped to the transaction, instead of a static map + global monitor; at minimum shard the monitor. Trade-off: session-attached state needs a reliable per-transaction hook for cleanup.
- **Regression test:** two concurrent `AfterCommit.localTx` blocks on different sessions each see only their own deferred actions; a rollback drops them.

### DOCS-6 — `clearSpace` and `clearAllData` evict the cache synchronously instead of after commit
- **Severity:** Low · **Likelihood:** Unlikely · **Confidence:** Confirmed (code)
- **Location:** `PostgresDocumentStore.scala:556-564` (`clearSpace` → `idsRemoved.foreach(id => cache.remove(id))`), `:604-609` and `:669-675` (`clearAllData` → `cache.clear()`). Contrast `removeDocument` (`:210-218`) and every other write, which go through `cacheAfterCommit` (drop now, store after commit, F16).
- **Preconditions:** `clearSpace`/`clearAllData` called inside a listener/`clearForRebuild` transaction (they take an implicit session; purge and targeted-rebuild call them in `subscriptionsState.localTx` — `ProjectionActor.scala:448`), with a concurrent reader of the same store (parallel projection, or a query thread).
- **Triggering scenario:** a purge's `clearForRebuild(OneSpace)` runs `clearSpace` inside the tx; a concurrent read loads a soon-to-be-deleted document into the cache between the synchronous `cache.remove` and the commit; the commit deletes the row, but the cache now holds it → a later read serves a document the database no longer has.
- **Failure mechanism:** eviction before commit is safe for the rollback direction (cache simply reloads), but unlike `cacheAfterCommit` it does not re-drop after commit, so a repopulation during the window survives. D53 (one writer per projection) and "run the purge while the organization is quiet" (H11) make a concurrent writer unlikely, which is why this is Low.
- **Impact:** a stale present cache entry for a purged/cleared document in a narrow race; wrong query result until the entry is evicted by another write or a restart. GDPR-adjacent (a purged document still served from cache) but only under the race and against the operational guidance.
- **Validation:** a `MapDocumentStoreCache`-backed store, a `clearSpace` inside a localTx, a concurrent `getDocument` that repopulates mid-transaction, assert the entry is gone after commit.
- **Recommended fix:** route `clearSpace`/`clearAllData` eviction through `cacheAfterCommit`/`AfterCommit(session)` (drop now, and again after commit), matching `removeDocument`. Trade-off: for `clearAllData` that means deferring a `cache.clear()`, trivial.
- **Regression test:** add the purge-under-concurrent-read case to `CachesAfterRollbackSpec`.

## Lesser findings (one line each)

- **Metrics tag maps allocated on every hot-path call even under the NoOp default:** `AggregateOwner.scala:508-509,623` and `ProjectionActor.scala:740` build `typeTag + (...) + (...)` `Map`s per command/persist/batch before calling `metrics`, so the default-off path still allocates — move the map build behind a cheap enabled check. (`metrics/Metrics.scala:22` NoOp.)
- **The `Metrics` "must not throw" contract is not enforced by the library:** calls like `AggregateOwner.scala:508` (post-commit Success branch) and `ProjectionActor.giveUp:777` are unguarded; a throwing host metrics impl escapes `receive` and can restart the owner right after a committed publish — wrap library-side `metrics.*` calls in a swallow-and-log.
- **`findDocumentByObjectInArray` interpolates `columnName` into SQL** (`PostgresDocumentStore.scala:396`, `WHERE $columnName #> ?`); safe today because the only caller passes the literal `"document"` (`:379`), but the `protected` overload is an injection point if ever called with external data — bind or allowlist it.
- **`ExpectedSingleTextValueLike` ILIKE patterns are host/user-supplied and bound but unconstrained** (`:348`, `:369`): a leading-`%` pattern cannot use a btree index → full scan, which combined with DOCS-1 (no limit) is an easy expensive query; no cost guard or note in SCALING.
- **`F171` `sameDefinition` compares `pg_indexes.indexdef` by crude string reduction** (`PostgresDocumentStore.scala:108-113`: strips all whitespace/parens, maps `::text[]`→`` and `::integer`→`::int`); different expressions that reduce equal would skip a needed rebuild, or a formatting change would rebuild unnecessarily (blocking writes) — brittle heuristic.
- **`MemoryDocumentStoreAutoId.generateNextId`** (`MemoryDocumentStore.scala:247-255`) uses `Random(System.nanoTime).nextLong()`, producing negative/zero keys unlike the Postgres sequence (≥1), and a `do/while` uniqueness loop; a test-double divergence that can surprise tests asserting positive/ordered ids.
- **`MemoryDocumentStore` backs its map with `scala.collection.parallel.mutable.ParHashMap`** (`:17`): `findDocument`'s `store.filter(...)` runs the reflective predicate in parallel on the FJ pool, and the map is not safe for concurrent structural writes under `parallelUpdateProcessing`; test-double only, but surprising.
- **`getDocuments(keys)` builds one `id IN (${toLoad})`** (`PostgresDocumentStore.scala:457`) with one bind per key; a very large key set can exceed PostgreSQL's ~65535 parameter limit and fail — chunk the IN list.
- **`reference.conf` ships `blocking-dispatcher` fixed-pool-size 32 but the host supplies the JDBC pool (ScalikeJDBC default 8)** (`reference.conf:10-17`); with the default pool, 32 threads contend for 8 connections (5 s wait → failed work). Documented in SCALING §1 and H8/H10 as a host step, but the default config alone is mismatched.

## Known, re-checked
- **F14 (test doubles) is incompletely closed for the document store:** its "still not mirrored" list names instant reads, permanent-delete clean-up and spaces, but not query ordering/paging — which `MemoryDocumentStore.findDocument` silently ignores (DOCS-3). ## Checked and safe
- **Nested DB connection inside an open session (pool deadlock lead):** the document store's finders/updates all route through `inSession` (reuses the caller's session) and F160 moved the two stragglers (`findDocumentByPath(ExpectedValue)`, `findDocumentByPaths`) onto the caller's session; no library doc-store path takes a second connection while a listener holds one.
- **Two nodes creating the same index / concurrent DDL:** `init()` and every `initSchema` run under `SchemaLock` (F63), so concurrent creation serializes; the advisory lock is released on crash (session-level on a dedicated connection) and in `finally`. (Startup-stall risk is DOCS-4, a different concern.)
- **Metrics tag cardinality:** tags are aggregate type / command / response / projection names and `subscriber.path.name` (`EventsBusActor.scala:348`, `AggregateOwner.scala:623`, `ClusterSerializer.scala:103`) — all bounded; no aggregate/user ids as tags, matching the §14 rule.
- **`Backoff` overflow:** the shift is capped (`math.min(..., 30)`) and ceilinged by `max.toMillis` (`Backoff.scala:16`); `first.toMillis << 30` stays well within `Long`; `gapRequests + 1` would need ~2e9 attempts to overflow `Int`.
- **`RandomUtil` seeding:** uses `ThreadLocalRandom` (`RandomUtil.scala:12`), no fixed seed; error-id strings are 16 chars from a 62-symbol alphabet — adequate.
- **Document-store version column overflow:** `version INT` increments per write; overflow needs ~2.1e9 writes to one document (decades at any realistic rate).
- **F16/F21 (cache-after-commit, lost updates on conflict):** `cacheAfterCommit` (`:493-504`) drops-then-defers with a newer-version guard, and `updateWithRetries`/`writeNextVersion` (`:512-553`) retry ≤10× evicting the stale entry — both correctly implemented for the update paths.
- **`findDocumentByObjectInArray` value handling (F158):** value bound as `?::jsonb` via an encoder, array path escaped and bound as `?::text[]` (`:383-404`) — no value injection.
- **mpjsons 0.7 `Option` write form:** verified from sources — default (non-compact) writes `None`→`{}`, `Some(v)`→`{"value":v}`, matching the memory store's `"value"` path special-casing; `NullPolicy.Fail` is the default. Consistent with F53/H4 (an absent Option reads as `None`), which remain open on the Neula side, not here.

## Open questions
- Does any Neula projection build a `DocumentStoreQuery` path or `Sort` field (or an index path) from end-user / request data? If so, DOCS-2 is an active SQL-injection path, not just a latent correctness bug — needs a grep of `neulaserver`.
- Are any Neula read models already large enough that `findDocumentByPath`/`findAll` without a limit (DOCS-1) can return millions of rows? A `SELECT max(count) FROM each projection_*` on a production copy would set the real likelihood.
- Does Neula run with the default 8-connection ScalikeJDBC pool or the recommended ≥32? If the default, the 32-thread blocking dispatcher already over-subscribes it under load (SCALING §1).
- Can a document-store `init` DDL realistically block during a cluster start window (autovacuum/long query on `events`/`aggregates`)? That decides DOCS-4's likelihood; needs a production timing/lock profile.
